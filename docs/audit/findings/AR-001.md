# AR-001: native GET submission before hydration

Severity: P1, privacy/release blocker on baseline. Owner: frontend. Baseline f865ee826c4965b1557c20b46c802f3e54138efc. Reproduction recorded8November2026 in AR-001-baseline.json; values are synthetic.

Precondition: JavaScript disabled, blocked or hydration not yet available. CalculatorForm rendered an enabled native form without method/action. Fill HPP materials317/labor211/overhead101/units7 and submit. Expected: client-only inputs must not enter navigation URLs or server requests. Actual: GET /kalkulator/hpp?materials=317&labor=211&overhead=101&units=7. Browser history and hosting access logs may retain these query values. This does not prove an attacker obtained data; it identifies a concrete unintended transmission path.

Isolated fix: shared CalculatorForm wraps its inputs and submit in a disabled fieldset until a mount effect confirms hydration, then removes only this temporary wrapper so existing row fieldsets and grouping stay unchanged. A visible noscript explanation states why computation is disabled. CSS only neutralizes the fieldset border/padding/margin and minimum width. No money engine, canonical, indexing or production setting changes. Disabled native controls cannot submit this data through the normal no-JS UI. Manually manipulating DOM via developer tools is outside this control's threat model.

Regression: tests/release-privacy.spec.ts checks all100SSR forms without JavaScript, disabled submit/fieldset, visible explanation and query-free URL; checks hydrated HPP still computes without navigation. Full existing suite, axe, reflow and visual audit must be repeated after this change. No claim of universal security conformance.
